# アーキテクチャと設計判断

## 1. 全体構成

Astro フロント（SSR）と Go の API を疎結合にし、両方を Vercel の 1 デプロイに載せる。

- フロントは `/api/resources`（Go）をサーバー側で fetch し、レベル別に整理済みの
  リソース一覧を描画する。
- Go 関数は Vercel の制約（`/api` 直下の各ファイルが個別ビルド）に合わせ、
  `api/index.go` 1 本に集約し、`r.URL.Path` で内部ディスパッチする。
  `vercel.json` で `/api/(.*)` → `/api/index` を rewrite。
- 実処理は `pkg/api/{resources,feedback}.go` に分離。これでローカルの
  `go build ./...` も素直に通り、テストも書ける。

### なぜこの技術構成か

| 選択 | 理由 | 却下した選択肢 |
|---|---|---|
| Astro | コンテンツ中心サイトに最適。ゼロ JS 寄りで SEO 有利。未経験なので学習も兼ねる | Next.js（既に別プロジェクトで使用済み、新規性がない） |
| Go | バックエンド軸の強化。将来モバイル（Flutter）から API 再利用可能 | TypeScript バックエンド（楽だが Go 学習の機会を失う） |
| 疎結合 | 認証を Go に集約でき、モバイル展開の余地が残る | フロント統合（モバイルで作り直しになる） |
| DB なし（MVP） | Vercel 1 デプロイに収める。MVP の主眼はスコアリングの説明であって永続化ではない | PostgreSQL + pgx + sqlc（フルスコープでは採用） |

## 2. 難易度スコアリング（中心的な技術要素）

### 原則

- **難易度と品質を別軸にする。** いいね数・ブクマ数は品質であって難易度ではない。
  UI では「♥ N（品質シグナル）」と難易度バッジを分けて表示する。
- **トピックごとの難易度ベクトルで持つ。** 例 `{ go: 3.9, docker: 1.0 }`。
  単一スカラーでは「Go は上級だが Docker は初級」という記事を表現できない。
- **各シグナルを 0..1 に正規化 → 加重和 → 0..5 にマップ。**
  重みは設定値（`scoring.DefaultWeights`）として外出しし、チューニング可能にする。

### シグナル（`pkg/scoring/`）

| シグナル | 取得方法 | 方向 | 既定重み |
|---|---|---|---|
| タグ | API のタグ名を辞書照合（`初心者`→易 / `内部実装`→難） | ± | 0.22 |
| 前提知識の明示 | 本文の正規表現（「〜は理解している前提」等） | 難 | 0.20 |
| 専門用語密度 | 用語辞書との照合（種類数 0.7 + 出現密度 0.3） | 難 | 0.20 |
| 説明の丁寧さ | 見出し数・図の数 | **易（負の重み）** | 0.10 |
| 一次資料リンク | RFC・論文・仕様書ドメインの出現数 | 難 | 0.13 |
| コード比率 | コードブロック行数 / 全行数 | 難 | 0.12 |
| 記事長 | 文字数（対数スケール） | 弱い難 | 0.03 |

各記事の結果は `Result.Signals` に**内訳付き**で返す（下記「検証」の理由）。

### レベル区分

難易度 0..5 を境界（`scoring.DefaultThresholds`、既定 1.8 / 3.2）で 3 区分。
加重和は全シグナルが同時に 1.0 になることがほぼ無く、実データはおおむね 1.0〜4.0 に
収まるため、境界は低めに置いている。手動正解セットとの相関を見ながら調整する前提。

### 検証（正解データが無いという最大の課題）

記事の「正しい難易度」は存在しないので、そのままでは精度を測れない。対策:

1. **シグナルの内訳を必ず返し、UI で開示する。** カードの「なぜこの難易度か」で
   各シグナルの寄与を横棒グラフ表示。まず人間が結果を評価できる状態を作る。
2. **明示フィードバックボタン（唯一の教師信号）。** 「簡単すぎた / ちょうど良い /
   難しすぎた」を収集する。
3. フルスコープでは手動で 50〜100 記事に難易度を付けた正解セットを作り、
   自動スコアとの相関を測る。**軸を足すより先に評価基盤を作る。**

## 3. ユーザーレベルとフィードバック

MVP では受け口（`POST /api/feedback`）のみ実装し、永続化はしない（202 を返す）。
フルスコープでの設計意図はコードのコメントに残している:

```
新レベル = 現レベル + K × (実際の結果 - 期待値)
期待値   = σ(ユーザーレベル - 記事難易度)
```

- コールドスタートは登録時アンケート（自己申告ではなく具体的行動で聞く）。
- 動的更新は Elo 方式。IRT は不採用（項目パラメータ推定に千人規模のデータが必要で、
  個人開発では集まらない）。
- マッチングは「少し上（+0.5〜1.0）」が最も学習効果が高いので、ガウシアンで
  「簡単すぎ」「難しすぎ」を両方減点する。

## 4. 著作権上の制約

- 保存・表示するのは**メタデータのみ**（タイトル・URL・タグ・著者・いいね数・公開日）。
- **本文の全文保存・転載は禁止。** `qiita.Item.Body` はスコア計算にのみ使い、
  レスポンスには含めない。
- 表示は「タイトル + 自作要約 + 出典明記 + 元記事へのリンク」。クリックで元サイトへ遷移。
- 現在の「自作要約」は本文先頭からの抽出。将来 LLM による 2〜3 文の要約に差し替える。
