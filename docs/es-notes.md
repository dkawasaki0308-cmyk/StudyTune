# 選考で説明する技術判断（メモ）

エントリーシート／面接で「何を・なぜそう決めたか」を話すための要点。
規模ではなく**説明できる技術判断**を見せることが目的。

## このプロダクトで一番語れること

**「正解データが存在しない推定タスクを、どう検証可能にするか」** に設計を寄せた点。

- 難易度スコアを出すだけなら加重和で終わる。難しいのは「その値が妥当かどう確かめるか」。
- 対策として (1) 全スコアにシグナル内訳を持たせて UI で開示、(2) フィードバックボタンを
  唯一の教師信号として最初から埋める、(3) 「軸を増やすより先に評価基盤」を原則にした。
- つまり **モデルの精度より、精度を測る仕組みを先に作った。**

## 個別の判断

| 判断 | 理由 | 却下した案 |
|---|---|---|
| 難易度と品質を分離 | いいね数は「良い記事」の指標であって「難しい記事」の指標ではない。混ぜると初心者に上級記事を勧めてしまう | いいね数を難易度の代理指標にする |
| トピック別の難易度ベクトル | 「Go は上級・Docker は初級」の記事を単一スカラーでは表せない | 記事に難易度スカラー 1 個 |
| ルールベース（加重和）+ 重み外出し | 個人開発でラベルが集まらない段階では、機械学習より調整可能なルールの方が説明・改善しやすい | 最初から学習モデル |
| IRT 不採用 | 項目パラメータの推定に千人規模の回答が要る。個人開発では集まらない。Elo なら 1 イベントから更新できる | IRT でユーザー能力と項目難易度を同時推定 |
| Go + Astro を疎結合 | 認証を Go に集約でき、将来 Flutter から同じ API を叩ける。バックエンド軸を強化したい | Next.js 単体（使用済みで新規性がなく、モバイルで作り直しになる） |
| MVP で DB を落とす | Vercel 1 デプロイに収めて選考までに動かすため。MVP の主眼は永続化ではなくスコアリングの説明 | PostgreSQL まで一気に作る（期限内に中途半端になる） |
| Qiita 失敗時にサンプルへフォールバック | API レート制限やオフラインでもデモが必ず動く。同じスコアリングを通すのでパイプラインの挙動は本物 | エラー画面を出す |
| Vercel の Go 関数を 1 本に集約 | `/api` 直下の複数ファイルが個別ビルドされる制約を回避しつつ、`go build ./...` とテストをローカルで通す | ファイルごとに関数を分ける（ローカルでビルドできない） |

## 数字・事実

- Go: 7 シグナルの加重和 → 0..5 → 3 区分。重み・境界は設定値。テスト 4 本
  （入門→初級 / 内部実装→上級 / 順序関係 / トピックベクトル）。
- サンプル 6 記事で難易度 0.4〜3.9 に分布し、初級 3 / 中級 1 / 上級 2 に分かれることを確認。
- フロントは SSR + クエリパラメータ駆動で、絞り込みに JS をほぼ使わない。
- 履歴は 1 目的 1 ブランチ → PR → マージコミット（GitHub Flow）。

## フルスコープとの差分（聞かれたら）

Elo による動的レベル更新、手動正解セット 50〜100 記事による精度検証、Meilisearch 検索、
